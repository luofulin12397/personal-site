四个取舍

都来自上面那几个仓库，改动前后的代码都还在。这里只写判断：为什么这么选、什么时候会失效。结构和代码片段放在拆解页里。

  1. 权限 · 知识库

    权限判定放在精排之后，denied 绝不联网兜底

    选了
    rerank → perm_filter → answer。只有放行的切片进提示词；全部被拦就短路出拒绝文案，跳过模型生成和缓存写入。联网兜底只在「向量路完全无召回、且未被权限短路」时触发。
    没选
    召回前先按权限过滤（省算力），或者把 web 检索当成第三条并行召回。
    代价
    无权内容也会被检索和精排一遍，算力白花；两道门（权限短路 / 无召回兜底）要一起维护，改一处得看另一处。
    失效
    知识库本身不做分级，或权限只有单一维度时，这套是纯多余的 300 行。

  2. 查询 · smart-bi

    不让模型写 SQL，只让它说意图

    选了
    模型输出 Intent，服务端按白名单指标和枚举维值编译成 QueryPlan。执行侧固定只读事务、固定角色、绝对期限。
    没选
    让模型直接生成 SQL 再执行，出了问题再靠提示词约束。
    代价
    每加一个指标都要写代码和测试，17 个测试文件是这么长出来的。问法超出白名单就只能追问。
    失效
    探索式分析：用户自己都还没想好切哪个维度时，白名单只会挡住路。

  3. 召回 · 知识库

    两路召回，融合之后再精排

    选了
    原查询一路、HyDE 假想答案一路，并行跑，进 rrf 按排名融合，再交给交叉编码器精排。
    没选
    单路向量召回，靠调大 top_k 补准确率；或者把 web 检索并进来凑第三路。
    代价
    每次查询多一次 HyDE 的模型调用；融合和精排各多一个调参点，参数之间会互相盖住。
    失效
    问题里是精确术语（型号、编码、人名）时，HyDE 会把原词改写掉，召回反而变差。

  4. 异步 · log-patrol

    写入口只留一个，用队列把它串起来

    选了
    文件 spool（pending/ → done/）当队列，常驻宿主一次只拉一个 run，串行跑完后移走。写入边界只有一处。
    没选
    并发跑多个 run，靠锁和事务解决冲突。
    代价
    吞吐被串行按死，积压时延迟线性上涨；单点，宿主挂了就不动了。
    失效
    单次 run 的耗时接近任务到达间隔时，队列永远追不上，串行成了瓶颈而不是保护。

这一页本身

没有框架，没有构建步骤，也没有 CDN。你正在看的这一页就是交付物，可以 view-source 逐行对。

  • 零构建

    一个 index.html、一份 CSS、一份 JS。双击能开，push 就上线，中间没有编译。页面源码是作品的一部分，不是构建产物。

  • 真终端

    help / ls / cat / explain / open 都能跑，↑↓ 翻历史，Tab 补公共前缀。关掉 JS，首屏那几行静态文本仍然是完整的。

  • 字体

    拉丁用 Archivo 和 Azeret Mono，中文按页面实际用字把 Noto Sans SC 子集成三个字重，全部自托管。断网不掉字形，Windows 和 macOS 断行一致。

  • 可读性

    正文对比度不低于 4.5:1，图里的字换算到屏幕也不小于 12px，焦点有 2px 描边，全部交互可用键盘完成，尊重 prefers-reduced-motion。

  • 刻意没有

    渐变标题、编号小标签、图标卡片网格、假的 QPS 和 P99、CTA 按钮、订阅框。页面上的数字都能在仓库里 find / wc / grep 数出来。
