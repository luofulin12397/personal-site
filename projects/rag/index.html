history_compress → item_name_confirm → access_control压历史、确认问的是哪份文档；判不出来就把问题抛回去，不猜

两路并行，不是三路

node_search_embedding原查询向量
node_search_embedding_hyde假想答案向量
node_rrf → node_rerank按排名融合，再交给交叉编码器精排

node_answer_output → node_save_cache只缓存成功生成的答案，拒绝文案不写进缓存

旁路：node_web_search_mcp 只在「完全没有召回、且未被权限短路」时触发。它没有连到 RRF，不是第三条并行召回路。

一次提问走过的十二个节点

这是 knowledge-base 里那张 LangGraph 查询图的真实形状。实线是主路径，虚线是两条旁路：命中缓存直接结束，无召回才去联网。 五个批注，对应一次提问路上的五个决定。图在宽屏上更清楚，这里先给结论。

  1. A

    入口先查缓存，两级

    人工审核过的 FAQ 优先，语义缓存其次。命中任何一个都直接返回，后面的检索和模型一次都不跑。省的不是毫秒，是整套调用链的钱。

  2. B

    判不出来就问回去，不猜

    认不准用户在问哪份文档时，这一层直接把问题抛回给用户，不往下走。猜错的代价是拿错文档编答案，比多问一句贵得多。

  3. C

    两路召回不是冗余

    一路拿原问题去查，一路先让模型写个假想答案再拿它去查。两路错的方式不一样，RRF 按排名融合才比单路稳。

  4. D

    权限卡在精排之后，denied 不联网

    四维（全局 / 部门 / 角色 / 个人）默认拒绝，只放行的切片进提示词。被拒的请求一律短路，不许走联网兜底，否则换个问法就能从公网拿到无权内容。

  5. E

    只缓存生成成功的答案

    权限短路的拒绝文案不写进缓存。把「你无权查看」缓存成答案，下一个人问同一句话就会拿到它，而且再也纠不回来。

三个决定，以及什么时候会失效

结构好抄，判断不好抄。这三条是画上面那张图时真正犹豫过的地方，每条都写清代价和失效条件。

  1. 权限判定收敛成纯函数，并且卡在精排之后

    perm_engine.py 在文件头写明自己是「单一权威实现」：不依赖数据库，输入 perms 和 user_ctx，输出一个布尔；配置接口、问答管线、后台任务一律复用，禁止散落第二份判定逻辑。图里把 node_perm_filter 放在 node_rerank 之后、node_answer_output 之前，提示词组装只拿到放行切片。

    代价：无权内容也会被检索和精排一遍，算力白花。失效：语料本身不分级、或权限只有单一维度时，这层是纯多余。

  2. denied 分支绝不触发联网兜底

    node_perm_filter_after 先检查 state["answer"]：权限短路或前置早退已经写了答案，就直接去生成；只有真的既没有 rrf_chunks 也没有 reranked_docs，才返回 node_web_search_mcp。这个顺序不能反，否则无权主题换个问法就能从公网拿到同类信息，四维边界被兜底旁路掉。

    代价：短路门和无召回门要一起维护，改一处得看另一处。失效：如果改成开放域助手、允许公网兜底回答任何问题，这条约束就不再成立，得换一种安全边界。

  3. 两路召回加 RRF，web 只做兜底

    源码把 node_search_embedding 和 node_search_embedding_hyde 分别 add_edge 到 node_rrf，node_access_control_after 的注释也明确写着「web 不再作为第三条并行召回路」。RRF 只按名次融合，两路分数量纲不同也不用归一化。

    代价：每次查询多一次 HyDE 的模型调用，而且名次融合扔掉了分数里的置信度。失效：问精确型号、编码、人名时，HyDE 的改写会把原词弄丢，召回反而更差。
